# Git workflow

## Полномочия

Без подтверждения выполняй только read-only команды: status, diff, log, show, blame, просмотр веток, тегов, remotes, upstream и конфигурации.

Перед любой операцией, меняющей рабочее дерево, индекс, refs, историю, remote или внешний сервис, запроси явное подтверждение. Это включает fetch, add, restore, stash, switch, создание веток, commit, pull, push, merge, rebase, cherry-pick, revert, reset, clean, теги, PR/MR, релизы, .gitignore, LFS, submodules и конфигурацию. Перечисли точные действия, ветки/remotes и эффект. После ошибки, конфликта или смены плана запроси новое подтверждение.

## Ветки и подготовка

1. Определи корень, ветку, upstream, remotes и состояние дерева. Прочитай проектные инструкции.
2. Не считай незакоммиченные изменения своими и не перезаписывай их.
3. Определи базу main или master. Перед рабочей веткой предложи fetch и fast-forward обновление базы.
4. Всегда запрашивай точное название новой ветки.
5. Не делай прямые commit и push в main/master; используй рабочую ветку и PR/MR.
6. Не переключай ветку при dirty worktree без безопасного решения. Удаление ветки согласуй после проверки merged/unmerged коммитов. После merge ветку не удаляй.

## Коммиты и синхронизация

- Русское сообщение: тип: область — изменение. Типы: feat, fix, refactor, docs; учитывай соглашение проекта. Номер задачи не добавляй.
- Атомарное дробление не обязательно; общий коммит по задаче допустим.
- Перед staging проверь diff и исключи посторонние файлы, секреты и артефакты. Показывать staged diff и сообщение отдельно не требуется.
- Amend — только после отдельного подтверждения.
- Перед pull/push/merge/rebase/cherry-pick проверь ветку, upstream, remote и диапазон коммитов. Для базы предпочитай pull --ff-only.
- Перед PR/MR предложи rebase на актуальную базу. При опубликованной ветке предупреди о переписывании истории.
- Force push запрещён в базе. В рабочую ветку допустим только --force-with-lease после подтверждения; --force не используй.

## Конфликты

Не удаляй, не прячь и не перезаписывай пользовательские изменения. Stash согласуй с точным scope. При конфликте остановись, перечисли файлы и варианты; не выбирай автоматически ours/theirs. После согласования исправь файлы и повтори проверки. Продолжение или отмена операции требует нового подтверждения.

## PR и MR

Используй gh для GitHub и glab для GitLab, если CLI установлен и авторизован. Не устанавливай и не авторизуй самостоятельно. Перед push проверь remote, ветку и upstream. Изменение remote согласуй. Для fork уточни push remote и источник PR/MR.

Создавай PR/MR в базу сразу готовым к review. Русский заголовок — как у коммита. Описание: цель, изменения, ключевые файлы, проверки, риски и откат. Reviewers, labels и milestone — только по указанию. Стратегия — merge commit. Не включай auto-merge и не сливай без отдельного подтверждения после проверки.

## Откат, теги и релизы

Для опубликованных изменений предпочитай revert. До reset --hard, clean, восстановления или удаления refs покажи точные данные, предупреди о потере и предложи безопасный вариант. Не удаляй untracked автоматически. Для clean отдельно согласуй dry run и удаление.

Формат версии определи по проекту, но версию всегда запрашивай. Релиз — из базы после принятого PR/MR. Создавай annotated tag с русским сообщением; создание и push согласуй отдельно. Подготовь changelog по проверенному диапазону и после подтверждения создай GitHub/GitLab Release.

## .gitignore, LFS, submodules и config

Перед .gitignore проверь существующие правила и tracked-файлы; удаление из индекса согласуй. Не коммить секреты, .env, IDE-кеши, зависимости и generated artifacts без требования проекта. Перед бинарными файлами проверь .gitattributes/LFS; изменения LFS согласуй. Операции submodule согласуй, показывая текущий и целевой commit.

Не меняй Git-конфигурацию. Используй существующую GPG/SSH-подпись; при ошибке обязательной подписи остановись. Сохраняй .gitattributes и LF/CRLF; не нормализуй массово. Не выводи credentials и токены.

## Отчёт

Сообщи ветку, действия, commit hash, push/upstream и URL PR/MR/релиза. Укажи невыполненное, конфликты и проверки. Не заявляй об успехе внешней операции без подтверждающего вывода.
