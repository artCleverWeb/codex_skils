# REST-клиент Bitrix

## Рабочий процесс

1. Определить продукт и редакцию: облачный Bitrix24, коробочный Bitrix24 или «1С-Битрикс: Управление сайтом»; зафиксировать домен, версию REST, доступные модули и способ авторизации.
2. Проверить каждый метод, параметр, scope, событие и формат ответа по фактическому порталу и официальной документации. Не переносить без проверки поведение облака в коробку и REST в REST 3.0.
3. Зафиксировать контракт: операции, объёмы, идентификаторы, направления синхронизации, консистентность и допустимые частичные ошибки.
4. Отделить HTTP-транспорт, авторизацию, DTO/маппинг и бизнес-логику. Для нового PHP-кода использовать PHP 8.2+, строгие типы и существующий HTTP-клиент проекта; новую зависимость сначала согласовать.
5. Реализовать пагинацию, batch и ограничение параллелизма по документированному контракту. Проверять ошибку каждого элемента batch.
6. Классифицировать ошибки. Повторять с ограниченным backoff только временные ошибки и учитывать серверную рекомендацию ожидания, если она передана.
7. Добавить идемпотентность, checkpoints и безопасное возобновление для массового импорта или экспорта.
8. Проверить happy path, пустые выборки, несколько страниц, истёкший токен, недостаточный scope, rate limit, сетевой сбой и частичный batch.

## Авторизация и данные

- Выбирать входящий вебхук только для ограниченной интеграции одного портала; OAuth-приложение — когда нужны пользовательская установка, несколько порталов или обновляемые токены.
- Не помещать webhook URL, `client_secret`, `access_token` и `refresh_token` в код, Git, сообщения об ошибках или журналы.
- Хранить токены зашифрованно или в штатном хранилище секретов; привязывать их к порталу и установке. Обновление токена выполнять атомарно и защищать от параллельного refresh.
- Валидировать базовый URL портала по allowlist/конфигурации; не позволять пользовательскому вводу превращать клиент в SSRF-прокси.
- Не считать HTTP 200 успехом: проверять REST-поля `error`, `error_description`, структуру `result` и ошибки вложенных команд.

## Массовые операции

- Запрашивать только нужные поля и использовать стабильный порядок вместе с пагинацией.
- Не предполагать фиксированный размер страницы или неизменность данных между страницами.
- Сохранять соответствие внешних и Bitrix ID отдельно от бизнес-данных.
- Для изменяющих операций задавать идемпотентный ключ на уровне приложения либо проверять достигнутое состояние перед повтором.
- Не запускать реальные массовые изменения, импорт или удаление без явного согласования.

## Источники

Перед реализацией прочитать [references/platform-matrix.md](references/platform-matrix.md). Для OAuth, событий, batch или лимитов дополнительно прочитать [references/client-checklist.md](references/client-checklist.md).

При расхождении источников доверять в порядке: фактический ответ и `methods` конкретного портала, установленный код коробки, официальная документация соответствующей версии. Существенные решения сопровождать ссылкой или путём к проверенному коду.
