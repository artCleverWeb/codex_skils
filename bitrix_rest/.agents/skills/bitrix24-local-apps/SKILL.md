# Локальные приложения Bitrix24

## Выбор сценария

1. Определить портал: облако или коробка; приложение: статическое, серверное с UI либо фоновое без UI.
2. Для простых вызовов одного портала рассмотреть webhook. Использовать локальное приложение, когда нужны UI-встраивание, события, установка или отдельная серверная логика.
3. Зафиксировать scope, placements, события, роли пользователей, публичные URL, модель хранения и требования к удалению.
4. Для PHP использовать 8.2+, `declare(strict_types=1)`, типизированные DTO и существующий HTTP-клиент проекта. Не навязывать D7 внешнему приложению; внутри коробочного проекта применять D7 и соглашения проекта.

## Жизненный цикл

1. Обработать установку как повторяемую операцию: проверить входные данные, сохранить портал и токены, зарегистрировать нужные события/placements и только затем подтвердить завершение установки.
2. Идентифицировать установку не только по пользователю: учитывать портал, application/client id и доступный идентификатор участника/установки.
3. Обновлять access token через refresh token атомарно; исключить одновременное обновление несколькими worker.
4. Обрабатывать переустановку, изменение scope, отключение приложения и отзыв доступа без создания дублей.
5. При удалении отключать события и фоновые задания, отзывать или удалять секреты и применять заранее согласованную политику пользовательских данных.

## События и интерфейс

- Проверять подлинность и принадлежность входящего события порталу/приложению доступным документированным способом; не доверять одним полям payload.
- Быстро подтверждать приём события, сохранять deduplication key и переносить тяжёлую обработку в очередь.
- Учитывать повторную доставку, нарушение порядка, удалённую сущность и временно недоступный REST API.
- Для iframe/placement проверять контекст, не выводить непроверенный HTML и задавать безопасные CSP/CORS/cookie-настройки с учётом встраивания.
- Использовать BX24 JavaScript SDK только для браузерного контекста портала; критические права и валидацию дублировать на сервере.
- Не запрашивать scopes и placements «на будущее».

## Эксплуатация

- Хранить секреты вне репозитория; шифровать токены и маскировать их в диагностике.
- Разделять tenant-данные и не принимать домен назначения из непроверенного запроса.
- Добавить correlation id, ограниченные retry, rate limiting, очереди и dead-letter/ручное восстановление для постоянных ошибок.
- Не выполнять установку на реальном портале, регистрацию событий, изменение данных или публикацию без явного согласования.

## Источники

Перед реализацией прочитать [references/local-app-checklist.md](references/local-app-checklist.md). Для транспорта и массовых вызовов также использовать `$bitrix-rest-client`.

Каждый метод, scope, placement, событие и поле установочного payload проверять по официальной документации и фактическому порталу; доступность зависит от редакции и версии.
