# Расширение REST API коробочного Bitrix

## Предварительные проверки

1. Проверить редакцию, версии ядра и модуля `rest`, наличие модуля и фактические сигнатуры API в установленном коде.
2. Найти существующие REST-регистрации проекта и продолжить принятые соглашения по module id, namespace, scope и именованию методов.
3. Уточнить потребителей, модель авторизации, контракт, обратную совместимость и необходимость собственного метода. Предпочесть штатный REST-метод, если он решает задачу.
4. Не изменять `/bitrix`; размещать реализацию в существующем модуле `/local/modules` либо согласованной структуре `/local`.

## Проектирование контракта

- Использовать стабильное пространство имён метода и явную версию контракта при несовместимых изменениях.
- Описать параметры, обязательность, форматы дат, enum, сортировку, пагинацию, результат и коды ошибок до реализации.
- Не раскрывать внутренние ORM-поля и исключения как публичный контракт.
- Сохранять прежние параметры и ответы либо выпускать новый метод/версию. Не менять семантику существующего метода молча.
- Для списков предусмотреть фильтр, выбор полей, предсказуемый порядок и ограничение размера ответа.

## Реализация

1. Регистрировать методы штатным механизмом модуля `rest`; не выполнять тяжёлую работу в обработчике события регистрации.
2. Проверять scope, контекст приложения и серверные права текущего пользователя для каждой операции. Наличие access token не заменяет проверку прав.
3. Нормализовать и валидировать вход по allowlist. Для записи использовать сервисы/D7 API и проверять `Result`.
4. Возвращать стабильные публичные ошибки без stack trace, SQL, путей и секретов.
5. Ограничивать объём и стоимость запроса; избегать N+1 и неконтролируемых ORM joins.
6. Делать изменяющие операции идемпотентными, если клиент может безопасно повторить запрос.
7. Регистрировать и снимать обработчики симметрично в жизненном цикле модуля.

## Безопасность и проверка

- Не использовать REST-обработчик как обход прав административного или внутреннего API.
- Не принимать имя класса, метода, поля ORM, путь к файлу или произвольный фильтр непосредственно от клиента.
- Маскировать токены, персональные данные и payload в журналах.
- Проверить вызов без авторизации, неверный scope, пользователя без прав, некорректные данные, границы пагинации, повтор запроса и совместимость прежнего клиента.
- Регистрацию модуля, изменение БД, чтение журналов и реальные REST-вызовы выполнять только после явного согласования.

## Источники

Перед изменениями прочитать [references/extension-checklist.md](references/extension-checklist.md). Точные ключи массива регистрации и сигнатуры обработчиков всегда сверять с установленной версией модуля `rest`; не восстанавливать их по памяти.
